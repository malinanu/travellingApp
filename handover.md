# Handover — latent-bug audit (2026-07-16)

## Why this exists

While fixing a reported bug (the vendor portal's "Menu" nav link silently
disappearing for real accounts — traced to a case-sensitive exact-string
category check in `web/vendor/components/shell.tsx` that didn't match
categories generated by other parts of the app), the user asked for a
proactive sweep for the same *class* of bug elsewhere: UI code that
branches on an enum-like string (status/category/role/type) without
handling every value that field can actually take in production, so it
fails silently instead of erroring loudly.

Two read-only audits were run against the real enum definitions
(`server/internal/domain/domain.go`) and the real data-generation code
(`server/internal/seed/seed.go`, `server/internal/gendata/generators.go`,
`server/internal/http/*.go`'s actual JSON responses) — one over the
vendor portal, one over the admin portal + the Flutter app. This file is
the result. `gh` (GitHub CLI) isn't installed in this environment and no
token is available, so the two real bugs below are written up as
ready-to-file issue content instead of actually being filed — copy either
block into a new GitHub issue as-is, or fix directly and delete this file.

## Issue 1 — Suspended vendors see the wrong message (and don't know why)

**Suggested title:** Vendor portal shows "Pending review" for suspended accounts, not a suspension notice
**Suggested labels:** `bug`, `vendor-portal`

**Description:**
`web/vendor/components/shell.tsx`'s `PendingGate` component (lines
237-260) renders a status-specific message when a vendor's account isn't
`approved`. It explicitly handles `'rejected'` and `'edits'`, but not
`'suspended'` — a real, admin-triggered status (`POST
/admin/vendors/{id}/suspend`, `server/internal/http/server.go:152`,
`domain.VendorSuspended` in `server/internal/domain/domain.go`). Any
`status` value other than `'rejected'`/`'edits'` — which today means only
`'suspended'`, since `'pending'` is the only other non-approved status and
*should* show this generic copy — falls through to:

```
"Pending review"
"Our team is reviewing your business. You will get access to the full
portal as soon as an admin approves it — usually within a day."
```

**Failure scenario:** An admin suspends a vendor from the admin command
center (Vendors → suspend). That vendor's next login shows "Pending
review… usually within a day" — implying a first-time application still
in the queue — rather than telling them their account was suspended and
why, or who to contact. They'll wait indefinitely for an approval that
will never come, or spam-retry, when the real,accurate message would set
correct expectations immediately.

**Suggested fix:** add a third branch for `status === 'suspended'` in both
the title (line 246) and body (lines 249-253) expressions, e.g.:
```tsx
{status === 'rejected' ? 'Application not approved'
  : status === 'suspended' ? 'Account suspended'
  : 'Pending review'}
```
and a body message explaining the account was suspended and how to
appeal/contact support (mirroring the `'rejected'` branch's
`partners@spotto.dev` contact pattern).

## Issue 2 — Admin "Change password" button does nothing

**Suggested title:** Admin profile page's "Change password" button has no handler
**Suggested labels:** `bug`, `admin-portal`

**Description:**
`web/admin/app/profile/page.tsx:39`:
```tsx
<button className="btn">Change password</button>
```
No `onClick`, no form, no navigation — clicking it is a complete no-op.
This is inconsistent with the rest of the same page: the 2FA
setup/enable/disable buttons directly below it (lines ~47-137) are fully
wired to `/auth/2fa/setup|enable|disable`, and the backend endpoint this
button should call, `PUT /auth/password`
(`server/internal/http/server.go:87`, `handleChangePassword` in
`server/internal/http/auth.go`), already exists and already works — it's
used by both the Flutter app's Security profile page and the vendor
portal's own `web/vendor/app/account/page.tsx` `PasswordSection`
component, which is a ready-made reference implementation to port over.

**Failure scenario:** An admin who wants to change their password clicks
the only button offered for it and nothing happens — no error, no
feedback, just silence. They have no way to change their password from
the admin portal at all today.

**Suggested fix:** port `PasswordSection` from
`web/vendor/app/account/page.tsx` (current-password + new-password
inputs, calls `PUT /auth/password`, stores the returned token via
`api.setToken`) into the admin profile page in place of the static button.

## Minor notes (not bugs today — flagged in case something nearby changes)

**3. `web/vendor/app/account/page.tsx` (~line 100)** — the "Verified"
badge's `business?.status === 'approved'` check is currently unreachable
as a false-negative risk: `Shell` already redirects any non-approved
vendor away before this page renders, so `business.status` is always
`'approved'` here today. It's the same fragile-exact-match shape as Issue
1 though — if the gating in `Shell` is ever loosened (e.g. to let
`'edits'`-status vendors preview their own account page), this check
would silently stop rendering "Verified" for them without erroring.
Nothing to do now; worth remembering if that gating changes.

**4. `web/admin/app/profile/page.tsx` (~lines 43-44)** — the "Role" card
hardcodes the string `"Super-admin — full platform access."` instead of
deriving it from `me.role` or similar. Harmless today since
`domain.Role` only has one admin tier, but it sits right next to fully
data-driven fields (`me?.name`, `me?.email`, `me?.totpEnabled`) on the
same page, so it'll be an easy thing to forget if a restricted-admin role
is ever introduced.

## What was checked and is clean (no need to re-audit from scratch)

- Every other status/category/role/type string comparison in
  `web/vendor/**/*.tsx` and `web/admin/**/*.tsx` was cross-checked against
  `domain.go`'s actual enum values and what `seed.go`/`generators.go`
  actually generate: offer status/type, claim status, feed status, vendor
  tier, subscription state, audio-guide depths, vendor role
  (`owner`/`staff`), user role, and validate-result strings all match
  exactly, case included.
- Every `api.get/post/put/patch/del` call across both portals maps to a
  route actually registered in `server/internal/http/server.go` — no
  requests that would 404.
- The Flutter app (`app/lib/**/*.dart`) has no vendor-category, offer-type,
  or feed-type string branching at all (place/offer types are only ever
  displayed, never compared), so this bug class doesn't apply there. The
  remaining `data/mock/*.dart` references are legitimate static reference
  catalogs (travel-style/interest picker lists) or explicitly-commented
  offline-first fallbacks — not silent substitutes for real API data.
- No leftover `TODO`/`FIXME`/`HACK` comments or `console.log`/`debugger`
  statements anywhere in `web/vendor`, `web/admin`, or `app/lib`.
- Non-functional-looking buttons elsewhere (vendor Growth's "Nudge all",
  event-promotion toggle, "Boost", BTS "Record/upload") are all
  intentionally disabled/labeled "coming soon" — not silently broken, just
  honestly deferred (payment processor / file-upload infra decisions
  pending, per this session's earlier scoping conversations).

## Methodology, if repeating this later

1. List every `enum`/status/role/category type in
   `server/internal/domain/domain.go`.
2. Grep the frontend (`web/**/*.tsx`, `app/lib/**/*.dart`) for string
   literals matching those values, and check every comparison branch
   handles every value the type can actually take — not just the ones a
   demo dataset happens to exercise.
3. Cross-check what `server/internal/seed/seed.go` and
   `server/internal/gendata/generators.go` actually generate for each
   field, since those (not just `domain.go`'s type definition) are what
   real accounts will actually have.
4. Grep every `api.<method>(` call site against
   `server/internal/http/server.go`'s registered routes.
